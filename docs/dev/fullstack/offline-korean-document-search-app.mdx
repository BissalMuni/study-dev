# 폐쇄망 한국어 문서검색 앱 아키텍처

외부망 없이 **단일 데스크톱 앱 안에서 한국어 문서 검색을 끝내는 도구**의 구조를 정리한다. 핵심 통찰은 두 가지다. 첫째, **자연어 검색은 LLM 없이도 된다**. 둘째, 모든 기술 선택이 *"서버 없이, 파이썬 없이, 외부망 없이 — 파일 동봉만으로 로컬 완결"* 이라는 한 방향을 향한다.

## 핵심 개념

```
┌─────────────────────────────────────────────────┐
│  React 19 + TypeScript + Tailwind CSS           │  ← UI (화면)
├─────────────────────────────────────────────────┤
│  Tauri 2 IPC                                    │  ← 브릿지 (JS ↔ Rust)
├─────────────────────────────────────────────────┤
│  Rust Backend (Clean Architecture)              │
│   Parsers   |   Indexer   |   Search Engine     │  ← 무거운 처리
│   hwpx/pdf  |   FTS5/벡터  |   키워드/시맨틱/RRF  │
├─────────────────────────────────────────────────┤
│  SQLite(FTS5) · usearch(HNSW) · ONNX 모델        │  ← 저장소
└─────────────────────────────────────────────────┘
```

- **UI** — 사용자가 보고 조작하는 화면.
- **브릿지** — 화면에서 무거운 작업을 Rust에 시키고 결과만 받아온다.
- **백엔드** — 파싱·인덱싱·검색·임베딩 같은 무거운 처리를 전부 담당.
- **저장소** — 만들어진 색인을 보관(원본 파일은 복사하지 않음).

## 앱 껍데기 — Tauri vs Electron

둘 다 웹기술(HTML/CSS/JS)로 데스크톱 앱을 만드는 같은 부류지만 무게가 다르다.

| | Electron | Tauri |
|---|---|---|
| 브라우저 엔진 | Chromium 번들 | OS 내장 WebView |
| 백엔드 언어 | Node.js | Rust |
| 앱 용량 | 보통 100MB+ | 수 MB에서 수십 MB |

**Tauri의 단점(폐쇄망 주의)**: OS WebView를 빌려 쓰므로 환경마다 엔진이 다르고(Windows=WebView2, macOS=WKWebView), **인터넷 안 되는 구버전 윈도우에는 WebView2가 없을 수 있다**. → Tauri의 **WebView2 동봉(embed) 옵션을 꼭 켜야** 한다.

**Rust를 쓰는 이유**: C++급 속도에 GC가 없고, 컴파일러가 소유권(ownership)으로 메모리 버그를 빌드 단계에서 차단한다. 폐쇄망 관공서 앱처럼 보안·안정성이 중요한 곳에 합리적.

## 상세 설명

### 자연어 검색을 AI 없이 하는 법 ★핵심

두 가지 고전적 방법을 RRF로 합치면 LLM 없이도 자연어 검색이 된다.

**(A) 키워드 검색 — 형태소 분석기로 변환**

```
"취득세를 감면받는 조건"
   ↓ Lindera(형태소 분석)로 의미 단위 분해
[취득세] [감면] [조건]            ← 조사·어미 떼어냄
   ↓ FTS5에 키워드로 검색 → BM25 점수로 정렬
```

- **Lindera** — 한국어 형태소 분석기(Rust). 한국어는 띄어쓰기로 단어가 안 나뉘므로, **자연어를 검색 키워드로 변환**하는 핵심. mecab-ko-dic 사전 사용.
- **FTS5** — SQLite 내장 전문검색 엔진. 미리 만든 역색인(단어→문서 목록)으로 빠르게 검색. **BM25 랭킹**으로 드문 핵심어가 많이 나온 문서를 위로 올린다.
- **약점** — 글자가 일치해야 함. `깎아주다` ≠ `감면`은 못 잡음.

**(B) 시맨틱 검색 — 미리 계산한 의미 좌표 거리 재기**

```
[인덱싱: 미리]   문서들 → KoSimCSE로 벡터화 → usearch에 저장
[검색: 실시간]   질문  → 즉석 벡터화      → usearch가 가까운 벡터 찾기
```

- AI가 "생각"하는 게 아니라 **미리 만든 좌표들 사이의 거리 계산(순수 수학)**.
- **KoSimCSE-roberta** — 한국어 **문장** 임베딩 모델(768차원). 단어 임베딩(Word2Vec)이 아니라 문장 단위라 문맥을 반영한다. 모델은 학습된 걸 다운로드해 쓰고, 내 문서의 벡터는 **내가 모델을 돌려서** 생성.
- **usearch** — 가벼운 벡터 **검색 엔진(라이브러리, DB 아님)**. HNSW 알고리즘으로 가장 가까운 벡터를 빠르게 근사 검색. 메타데이터는 옆의 SQLite가 담당.
- **강점** — `깎아주다`와 `감면`을 의미로 매칭. 키워드의 약점 보완.

**(C) RRF로 병합** — 키워드 순위와 시맨틱 순위를 `1/(k+순위)`로 합산. 점수 스케일이 다른 두 검색을 안정적으로 합치는 표준 방법.

> **결론**: 키워드(Lindera+FTS5) + 시맨틱(KoSimCSE+usearch) + RRF = LLM 없이도 자연어 검색 완성. LLM(Gemini)은 검색이 아니라 "찾은 결과로 답변 문장 만들기(RAG)"에만 쓰인다.

### 인덱싱 — 검색을 빠르게 하려는 선행 작업

인덱싱은 책 맨 뒤의 "찾아보기(색인)"를 미리 만들어두는 것. 무거운 일을 검색 순간이 아니라 미리 끝내둔다.

- **시간**: 최초 1회 무거움(이후 파일감시로 증분만). 진짜 병목은 임베딩이 아니라 **OCR**.
- **용량**: 의외로 가볍다. 벡터 1개 = 768차원 × 4바이트(FP32) ≈ 3KB → 10만 청크 ≈ 300MB. **원본 파일은 복사하지 않고 경로만 저장**한다.
- **모델 교체 주의**: 임베딩 모델을 바꾸면 좌표계가 바뀌어 전부 재인덱싱해야 한다.

**청킹** — 문서를 통째로 벡터 1개로 만들지 않고 **청크(조각)로 쪼개 청크마다 벡터 1개**를 만든다(통째로 누르면 의미가 뭉개지고 어느 부분이 답인지 못 짚음).

DB에 저장되는 최종 모습:

```
청크ID | 원본문서경로          | 위치  | 추출텍스트       | 벡터(768)
-------|----------------------|-------|-----------------|----------
  1    | D:\문서\보고서.hwpx  | p.1   | "취득세는..."    | [0.1,...]
  2    | D:\문서\보고서.hwpx  | p.3   | "감면 대상은..." | [0.3,...]
```

**경계 문제와 overlap** — 청크를 딱 끊으면 경계에 걸친 의미가 잘린다(취득세는 청크1, 감면은 청크2). 해법은 공백 벡터화가 아니라 **청크를 10~20% 겹쳐서 자르기(overlap)**. 더해서 **의미 단위 경계(문단·문장·조/항/호)로 자르기**는 AI 없이 규칙(패턴 매칭)으로 가능하다. 세무·법령 문서는 구조가 칼같아 규칙 기반이 특히 잘 맞는다.

### AI 모델을 로컬에서 돌리는 법 — ONNX

**ONNX = AI 모델 버전의 PDF.** PyTorch·TensorFlow로 만든 모델을 중립 포맷으로 빼두면 그 프레임워크 없이 어디서든 실행된다. 단 PDF는 *읽는 문서*를 담고, ONNX는 *실행되는 모델*(계산 그래프 + 가중치)을 담는다. **ONNX Runtime**이 그 `.onnx`를 실행하는 엔진이라 앱엔 이것 + 모델파일만 있으면 된다(파이썬 불필요).

단, 모델 옆에 전·후처리가 세트로 붙는다 — 임베딩엔 `tokenizer.json`(HuggingFace `tokenizers` 크레이트), OCR엔 검출/인식 모델 2개 + 문자 사전. Rust 표준 경로는 `ort` + `tokenizers` 크레이트.

**양자화와 정확도** — 순수 ONNX 변환만으로는 정확도가 거의 안 떨어진다(소수점 뒷자리, 무시 가능). 진짜 범인은 **양자화**(가중치 정밀도를 FP32→INT8로 낮춤)다.

| 자료형 | 용량 | 정확도 | 추천 |
|---|---|---|---|
| FP32 | 큼 | 원본 | 임베딩은 이걸로 시작 |
| FP16 | 1/2 | 거의 동일 | GPU 있으면 |
| INT8 | 1/4 | 1~3% 손실 | 용량/속도 급할 때만 |

정밀도를 유지하면(양자화 안 하면) 정확도가 보존된다. **세무·법률 문서는 정확도 우선이라 양자화 없이 FP16/FP32 권장.** 검증은 같은 문장 100개를 원본 vs ONNX로 벡터화해 **코사인 유사도 0.999+면 정상**.

### 문서 읽기와 OCR

- **HWP 파싱** — `kordoc`은 공무원이 만든 신뢰도 높은 파서지만 Node.js 기반이라 Rust 앱과 스택이 안 맞아 제외. 순수 Rust 대안은 `hwpers`(HWP 5.0 바이너리), `hwp-rs`, `rhwp`. **구형 바이너리 `.hwp`까지 읽는지** 꼭 확인(관공서엔 옛날 파일이 많음).
- **PaddleOCR** — 정확도는 입력 상태에 따라 천차만별(깨끗한 인쇄=높음, 흐릿한 스캔/표/손글씨=낮음). 한국어 전용 `korean_PP-OCRv5_mobile_rec` 사용, 권장 해상도 1080p–2K. **OCR 결과는 검색 인덱스로만 쓰고 원문 확인은 사람이** 하는 구조가 안전.

## 핵심 정리

> 1. **"자연어 검색 = AI"가 아니다.** 형태소 분석(Lindera)으로 자연어를 키워드로 바꾸고, 미리 계산한 벡터 거리(시맨틱)로 의미를 보완하면 LLM 없이도 자연어 검색이 된다. AI(Gemini)는 마지막 "답변 작성"에만 쓰인다.
> 2. **모든 선택이 "로컬 완결"로 일관.** Tauri(서버 불필요), usearch(DB 서버 불필요), ONNX(파이썬 불필요) — 전부 파일 동봉만으로 폐쇄망에서 돌게 하는 한 방향이다.

| 기술 | 한 줄 |
|---|---|
| Tauri | Electron의 가벼운 버전(OS WebView + Rust) |
| Rust | C++급 속도 + 메모리 안전 |
| Lindera | 자연어→키워드 변환 형태소 분석기 (AI 아님) |
| FTS5 | SQLite 내장 키워드 검색(BM25) |
| KoSimCSE | 문장→의미 벡터(768차원) 임베딩 |
| usearch | 벡터 거리 검색(HNSW, DB 아님) |
| RRF | 키워드+시맨틱 결과 병합 |
| ONNX / Runtime | AI 모델 버전의 PDF / 그 실행 엔진 |
| PaddleOCR | 스캔문서→텍스트 |
