# 디버깅 로그: 키움 REST API 500 에러 해결 과정

## 웹앱 아키텍처 계층 구조

이 프로젝트는 4개의 계층으로 구성되며, 각 문제가 어느 계층에서 발생했는지 표시한다.

```
┌─────────────────────────────────────────────────────────┐
│  [L1] Browser (Client)                                  │
│  - React 컴포넌트가 fetch() 호출                          │
│  - 요청: GET/POST http://localhost:3000/api/py/...       │
└──────────────────────┬──────────────────────────────────┘
                       │  HTTP 요청
┌──────────────────────▼──────────────────────────────────┐
│  [L2] Next.js (Proxy / Frontend Server)                 │
│  - next.config.ts의 rewrites 규칙으로 프록시              │
│  - /api/py/:path* → http://localhost:8000/:path*        │
│  - 정적 파일, SSR 페이지도 여기서 처리                     │
└──────────────────────┬──────────────────────────────────┘
                       │  프록시된 HTTP 요청
┌──────────────────────▼──────────────────────────────────┐
│  [L3] FastAPI (Backend API Server)                      │
│  - 라우팅: /api/stocks, /api/analyze 등                  │
│  - 비즈니스 로직: 데이터 수집, 분석, 캐싱                   │
│  - .env 로드, 인증 토큰 관리                              │
└──────────────────────┬──────────────────────────────────┘
                       │  외부 API 요청
┌──────────────────────▼──────────────────────────────────┐
│  [L4] External API (Kiwoom REST API)                    │
│  - OAuth2 토큰 발급: /oauth2/token                       │
│  - 차트 데이터: /api/dostk/chart (api-id: ka10081)       │
│  - 연속조회: cont-yn / next-key 헤더                     │
└─────────────────────────────────────────────────────────┘
```

## 증상

- 브라우저에서 종목코드 입력 후 "수집" 클릭 → `500 Internal Server Error`
- 요청 URL: `http://localhost:3000/api/py/api/stocks/009830/fetch`

### 요청 흐름 추적

```
Browser → [L1] fetch("/api/py/api/stocks/009830/fetch")
       → [L2] Next.js rewrites → http://localhost:8000/api/stocks/009830/fetch
       → [L3] FastAPI fetch_stock() → fetch_daily_ohlcv()
       → [L3] get_access_token() → requests.post(...)
       → [L4] Kiwoom API /oauth2/token → ❌ 404 Not Found
       → [L3] 예외 발생 → 500 Internal Server Error
       → [L2] 500 그대로 전달
       → [L1] "종목 009830 수집 실패"
```

## 1차 문제: API Base URL 오류

**계층: [L3] Backend → [L4] External API 경계**

### 원인
`python/kiwoom/auth.py`에서 키움 API Base URL을 잘못 설정함.

```python
# ❌ 잘못된 URL (API 문서에 혼재되어 있는 URL)
BASE_URL = "https://openapi.kiwoom.com"

# ✅ 올바른 URL (실제 REST API 엔드포인트)
BASE_URL = "https://api.kiwoom.com"
```

### REST vs WebSocket — 왜 URL이 다른가?

키움은 통신 방식에 따라 서버를 분리해 놓았다.

**REST (`api.kiwoom.com`)** — 요청-응답 방식

```text
클라이언트 → 요청 → 서버 → 응답 → 연결 끊김
```

- 매 요청마다 독립적 (stateless)
- 용도: 차트 데이터 조회, 토큰 발급 등 **한번 물어보고 답 받으면 끝**인 작업

**WebSocket (`openapi.kiwoom.com`)** — 양방향 연결 유지

```text
클라이언트 ↔ 서버 (연결 유지)
  서버: "삼성전자 72,000원"
  서버: "삼성전자 72,100원"  ← 안 물어봐도 보내줌
  서버: "삼성전자 71,900원"
```

- 한번 연결하면 서버가 알아서 데이터를 보내준다
- 용도: **실시간 시세**, 체결 알림 등 계속 업데이트가 필요한 작업

| | REST | WebSocket |
|---|---|---|
| 비유 | 택배 주문 (주문할 때마다 새로 요청) | 전화 통화 (연결 후 계속 대화) |
| 연결 | 매번 새로 | 한번 맺고 유지 |
| 데이터 방향 | 클라이언트 → 서버 → 클라이언트 | 양방향 (서버가 먼저 보낼 수 있음) |
| 프로토콜 | HTTP | WS (WebSocket) |

> 이 프로젝트는 과거 차트 데이터를 한번 조회하는 것이므로 REST(`api.kiwoom.com`)가 맞다.
> 실시간 시세 스트리밍이 필요하면 그때 WebSocket(`openapi.kiwoom.com`)을 쓰게 된다.

### 왜 이 계층에서 발생했나?

- L3(FastAPI)에서 L4(키움 API)로 나가는 **외부 통신의 엔드포인트 설정 오류**
- 키움 공식 문서에 `openapi.kiwoom.com`(WebSocket용)과 `api.kiwoom.com`(REST용)이 혼재
- WebSocket URL을 REST API URL로 착각

### 진단 방법
```bash
# L3 → L4 구간만 격리해서 테스트
python -c "
from kiwoom.auth import get_access_token
try:
    token = get_access_token()
except Exception as e:
    print('Error:', type(e).__name__, str(e))
"
# → HTTPError 404 Client Error: Not Found for url: https://openapi.kiwoom.com/oauth2/token
```

### 교훈
> 외부 API 연동 시, 문서에 나온 URL이 여러 개일 때 각각의 용도(REST vs WebSocket vs Mock)를 구분해야 한다. 기존에 작동하는 코드가 있으면 반드시 참고한다.

## 2차 문제: OAuth 요청 필드명 오류

**계층: [L3] Backend → [L4] External API 경계**

### 원인
토큰 요청 시 body 필드명이 틀림.

```python
# ❌ 잘못된 필드 (추측으로 작성)
json={"grant_type": "client_credentials", "appkey": app_key, "appsecretkey": app_secret}

# ✅ 올바른 필드 (실제 API 스펙)
json={"grant_type": "client_credentials", "appkey": app_key, "secretkey": app_secret}
```

### 왜 이 계층에서 발생했나?
- L3에서 L4로 보내는 **요청 포맷의 필드명 불일치**
- 키움 API는 에러 메시지가 불명확하여 어떤 필드가 잘못됐는지 알기 어려움
- `appsecretkey` vs `secretkey` — 미묘한 네이밍 차이

### 해결
- 기존 `bokstock-trading` 프로젝트의 동작하는 코드에서 정확한 필드명 확인
- `Content-Type: application/json;charset=UTF-8` 헤더도 맞춤
- `api-id` 헤더 방식 도입 (URL path 대신 헤더로 TR 코드 전달)

### 교훈
> 외부 API의 필드명은 추측하지 말고, 동작하는 레퍼런스 코드나 공식 예제를 정확히 따라야 한다.

## 3차 문제: API 응답 필드명 불일치

**계층: [L3] Backend 내부 (응답 파싱)**

### 원인
인증은 성공했지만, L4에서 받은 응답 JSON의 키 이름이 코드의 예상과 달랐음.

| 코드에서 사용한 키 | 실제 응답 키 | 의미 |
|---|---|---|
| `output` | `stk_dt_pole_chart_qry` | 봉 데이터 배열 |
| `open` | `open_pric` | 시가 |
| `high` | `high_pric` | 고가 |
| `low` | `low_pric` | 저가 |
| `close` | `cur_prc` | 종가(현재가) |
| `vol` | `trde_qty` | 거래량 |

### 왜 이 계층에서 발생했나?
- L4의 응답을 L3에서 파싱하는 **데이터 매핑 계층**의 문제
- 에러가 아닌 **빈 데이터**로 나타남 (잘못된 키로 접근 → None → 0건)
- 500 에러가 아니라 "정상 응답이지만 빈 결과"라서 발견이 늦어짐

### 진단 방법
```bash
# L4 응답 원본(raw JSON)을 직접 확인
python -c "
import requests, json
from kiwoom.auth import BASE_URL, get_headers
headers = get_headers(api_id='ka10081')
body = {'stk_cd': '009830', 'base_dt': '20260411', 'upd_stkpc_tp': '1'}
resp = requests.post(f'{BASE_URL}/api/dostk/chart', headers=headers, json=body, timeout=30)
print(json.dumps(resp.json(), indent=2, ensure_ascii=False)[:1000])
"
```

### 교훈
> 외부 API 연동 시, 반드시 raw 응답을 먼저 확인하고 파싱 코드를 작성한다. "0건 반환"은 에러가 아닌 매핑 오류일 수 있다.

## 4차 문제: 연속조회 헤더 방식 변경

**계층: [L3] Backend → [L4] External API 경계 (페이지네이션)**

### 원인
연속조회(pagination) 키 위치가 응답 body가 아닌 **응답 헤더**에 있었음.

```python
# ❌ body에서 찾음
next_key = data.get("next_key", "")

# ✅ 헤더에서 찾음
resp_next = resp.headers.get("next-key", "")
resp_cont = resp.headers.get("cont-yn", "N")
```

### 왜 이 계층에서 발생했나?
- REST API의 **페이지네이션 프로토콜 불일치**
- 일반적인 REST API는 body에 `next_cursor`나 `next_page`를 넣지만, 키움 API는 HTTP 헤더를 사용
- 비표준적 설계이므로 문서/레퍼런스 코드 없이는 알기 어려움

### 교훈
> 페이지네이션 정보는 API마다 body, header, Link 헤더 등 위치가 다르다. 첫 응답의 헤더를 반드시 확인한다.

## 5차 문제: .env 파일 경로 미탐지

**계층: [L3] Backend 내부 (환경 설정)**

### 증상
CLI에서 직접 `python -c "..."` 실행하면 성공하지만, uvicorn으로 실행하면 500 에러.

### 원인
```
프로젝트 구조:
bokstock-analysis/
├── python/
│   ├── .env          ← API 키가 여기에 있음
│   ├── main.py
│   └── kiwoom/
│       └── auth.py   ← load_dotenv()가 여기서 호출됨
```

- `load_dotenv()`는 **현재 작업 디렉토리(CWD)**에서 `.env`를 찾음
- CLI: `cd python && python -c "..."` → CWD = `python/` → `.env` 발견 ✅
- uvicorn: 실행 위치에 따라 CWD가 다를 수 있음 → `.env` 미발견 ❌

### 해결
```python
# CWD에 의존하지 않는 절대 경로
from pathlib import Path
_env_path = Path(__file__).resolve().parent.parent / ".env"
load_dotenv(_env_path)
```

### 왜 이 계층에서 발생했나?
- L3 서버 프로세스의 **실행 환경(CWD) 차이**
- 개발 중 CLI 테스트와 서버 실행의 컨텍스트가 다름
- "내 컴에서는 되는데 서버에서는 안 됨" 패턴의 전형적 사례

### 교훈
> 환경변수/설정 파일 로드 시 CWD 의존성을 제거하고, `__file__` 기반 절대 경로를 사용한다.

## 6차 문제: 포트 충돌 (좀비 프로세스)

**계층: [L3] Backend (OS/인프라 레벨)**

### 증상
uvicorn 재시작 시 `[Errno 10048] error while attempting to bind on address ('127.0.0.1', 8000)`

### 원인
이전 uvicorn 프로세스가 완전히 종료되지 않아 포트 8000을 점유 중 (좀비 프로세스).

### 진단 → 해결
```bash
# 1. 포트 점유 프로세스 확인
netstat -ano | grep ":8000 " | grep LISTEN
# → TCP  127.0.0.1:8000  0.0.0.0:0  LISTENING  31228

# 2. 프로세스 강제 종료 (Windows bash에서는 //F)
taskkill //F //PID 31228

# 3. 포트 해제 확인
netstat -ano | grep ":8000 " | grep LISTEN  # 출력 없으면 OK

# 4. 서버 재시작
uvicorn main:app --port 8000
```

### 왜 이 계층에서 발생했나?
- 코드 문제가 아닌 **OS 레벨 리소스(포트) 관리 문제**
- `--reload` 모드에서 파일 변경 감지 → 워커 재시작 과정에서 불완전 종료 발생
- Windows 환경 특유의 프로세스 정리 지연

### 주의: Windows bash 환경
```bash
# ❌ bash가 /F를 파일 경로로 해석
taskkill /F /PID 12345

# ✅ 슬래시를 이스케이프
taskkill //F //PID 12345
```

### 교훈
> 서버가 안 뜰 때 코드 문제가 아닌 포트 충돌일 수 있다. `netstat`으로 먼저 확인한다.

## 계층별 문제 요약

```
┌──────────────────────────────────────────────────────────────┐
│  계층                    │ 문제        │ 핵심 원인            │
├──────────────────────────┼─────────────┼──────────────────────┤
│  [L3→L4] API 통신        │ 1차: URL    │ REST vs WebSocket URL│
│  [L3→L4] API 통신        │ 2차: 인증   │ 요청 필드명 불일치    │
│  [L3] 응답 파싱           │ 3차: 매핑   │ 응답 필드명 불일치    │
│  [L3→L4] 페이지네이션     │ 4차: 연속   │ body vs header 위치  │
│  [L3] 환경 설정           │ 5차: .env   │ CWD 의존성           │
│  [L3] OS/인프라           │ 6차: 포트   │ 좀비 프로세스         │
└──────────────────────────────────────────────────────────────┘
```

### 패턴 분석

**모든 문제가 L3(Backend) 계층에서 발생했다.** 이유:

1. **L1(Browser)**: React 컴포넌트는 단순 fetch — 문제 발생 여지가 적음
2. **L2(Next.js Proxy)**: rewrites 설정만 하면 투명하게 전달 — 문제 없음
3. **L3(FastAPI)**: 외부 API와의 **통합 지점(integration point)**이며, 환경 설정/프로세스 관리까지 책임 → 문제 집중
4. **L4(키움 API)**: 우리가 수정할 수 없는 외부 시스템 — L3에서 맞춰야 함

> **핵심 교훈**: 외부 API 연동 코드는 반드시 동작하는 레퍼런스를 기반으로 작성하고,
> raw 요청/응답을 먼저 확인한 후 파싱 코드를 작성한다.

## 프록시 구간의 TCP 3-Way Handshake

### 질문: 브라우저→Next.js→FastAPI로 갈 때 매번 3-way handshake가 발생하는가?

```text
브라우저 ──TCP 연결 1──→ Next.js ──TCP 연결 2──→ FastAPI
         (3-way handshake)       (3-way handshake)
```

### 구간별 분석

**브라우저 → Next.js (localhost:3000)**

- TCP 연결이므로 **3-way handshake 발생** (SYN → SYN-ACK → ACK)
- 단, 브라우저는 HTTP/1.1 Keep-Alive 또는 HTTP/2를 사용하므로 **첫 요청에서만** handshake가 발생하고, 이후 요청은 같은 연결을 재사용

**Next.js → FastAPI (localhost:8000)**

- Next.js가 rewrite로 FastAPI에 요청할 때 **별도의 TCP 연결**이 생성됨
- Next.js는 내부적으로 `fetch`(또는 `http.request`)를 사용하므로 여기서도 **3-way handshake 발생**

### localhost이므로 비용은 거의 없다

두 handshake 모두 **네트워크를 타지 않는다.** `localhost`는 OS의 loopback 인터페이스(`127.0.0.1`)를 통해 커널 내부에서 처리되므로:

- 물리적 네트워크 카드를 거치지 않음
- RTT(왕복 시간)가 거의 **0.01ms 이하**
- 패킷 손실 없음

### 정리

| 구간 | 3-way handshake | 실제 비용 |
|---|---|---|
| 브라우저 → Next.js | O (첫 요청만, 이후 Keep-Alive) | 거의 없음 (localhost) |
| Next.js → FastAPI | O (첫 요청만, 연결 재사용 가능) | 거의 없음 (localhost) |
| 배포 환경에서 서버가 분리되면 | O | **네트워크 RTT가 실제로 발생** |

> **핵심**: handshake는 2번 발생하지만, localhost 환경에서는 실제 체감 지연이 무시할 수 있는 수준이다. 배포 시 서버가 물리적으로 분리되면 그때 RTT 비용이 실제로 발생한다.

## 웹앱 계층별 학습 포인트

| 계층 | 역할 | 이 프로젝트에서 배울 점 |
|---|---|---|
| **L1 Client** | UI 렌더링, 사용자 입력, API 호출 | React state 관리, fetch 에러 핸들링 |
| **L2 Proxy** | 요청 라우팅, CORS 우회, URL 마스킹 | Next.js rewrites, 프록시 패턴 |
| **L3 Backend** | 비즈니스 로직, 인증, 데이터 처리 | FastAPI, 외부 API 연동, 환경변수 관리 |
| **L4 External** | 서드파티 API (우리가 수정 불가) | API 스펙 정확히 읽기, raw 응답 검증 |
| **인프라** | 포트, 프로세스, 네트워크 | netstat, taskkill, 프로세스 디버깅 |
