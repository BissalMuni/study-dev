# Git 내부 단계 구조와 명령어 매핑

`git status`가 "up to date"라고 했는데 실제 서버에는 새 커밋이 있던 사례에서 출발한다.
원인은 단순했다 — Git의 명령어 대부분이 **로컬 파일만 보고 네트워크는 안 친다**. 어떤 단계가 있고 어느 명령어가 어디를 건드리는지 정확히 알면 이런 혼동이 사라진다.

## 핵심 개념

Git에는 사실상 **5개 단계**가 존재한다. 왼쪽 4개는 모두 로컬 `.git/` 안에 있고, 가장 오른쪽 1개만 네트워크 너머에 있다.

```
작업트리 ── 인덱스(스테이징) ── HEAD/refs/heads/<br> ── refs/remotes/origin/<br> ── 실제 서버
  (0)         (1)                      (2)                       (3)                  (4)
                                                                                       ↑
                                                                              네트워크 경계
```

| # | 이름 | 실제 위치 | 의미 |
|---|---|---|---|
| (0) | 작업트리 (working tree) | 프로젝트 폴더의 실제 파일 | 지금 편집 중인 사본 |
| (1) | 인덱스 (index / staging area) | `.git/index` (바이너리) | `git add`로 올린 다음 커밋 후보 |
| (2) | 로컬 브랜치 (HEAD) | `.git/refs/heads/main` | 내가 커밋한 결과의 최신 위치 |
| (3) | 원격 추적 브랜치 | `.git/refs/remotes/origin/main` | **마지막 fetch 시점**의 서버 사진 |
| (4) | 실제 서버 | GitHub 등 원격 저장소 | 진짜 원본 — fetch 전엔 모름 |

핵심: **(3)은 "원격의 실시간 상태"가 아니라 "지난번 fetch 때 본 스냅샷"이다.** 이걸 놓치면 `git status`의 "up to date"를 오해하게 된다.

## 상세 설명

### HEAD와 refs/heads/main의 관계

```
.git/HEAD                        →  "ref: refs/heads/main"   (포인터의 포인터)
.git/refs/heads/main             →  4806c184e1580ed5...      (실제 커밋 SHA)
.git/refs/remotes/origin/main    →  b012edef470c8df1...      (서버 사진)
```

`HEAD`는 "지금 어느 브랜치에 있는지"만 가리키고, 그 브랜치의 실제 커밋은 `refs/heads/<branch>`가 들고 있다. 둘은 거의 항상 같이 움직이므로 일상적으로는 "HEAD = 내 브랜치 끝"으로 봐도 무방하다.

### 비유

```
HEAD/refs/heads/main           = 내 책상 위 작업물 (내가 커밋한 결과)
refs/remotes/origin/main       = "지난번 서버 갔을 때 찍어 둔 사진 한 장"
실제 서버 origin/main          = GitHub에 있는 진짜 — fetch 전엔 알 수 없음
```

## 명령어가 어느 단계를 건드리는가

### 데이터를 옮기는 명령어

| 명령어 | 구간 | 방향 | 네트워크 |
|---|---|---|---|
| `git add` | (0) → (1) | 작업트리 → 인덱스 | X |
| `git commit` | (1) → (2) | 인덱스 → 로컬 브랜치 | X |
| `git checkout <br>` | (2) → (0) | 브랜치 → 작업트리 | X |
| `git fetch` | (4) → (3) | **서버 → 로컬 스냅샷만** | O |
| `git merge origin/main` | (3) → (2) → (0) | 스냅샷 → 내 브랜치 → 작업트리 | X |
| `git pull` | (4) → (3) → (2) → (0) | fetch + merge 합본 | O |
| `git push` | (2) → (4) | 내 브랜치 → 서버 (+ (3) 갱신) | O |

핵심 포인트:

- **`git fetch`는 (3)만 건드린다.** (0), (1), (2)는 절대 안 건드리므로 안전하다.
- **`git pull`은 (3)에서 끝나지 않고 (2), (0)까지 자동 진행**되므로 작업 중인 코드와 충돌할 수 있다.
- **`git push`는 (2)→(4)로 보내면서 부수효과로 (3)도 갱신**된다.

### 단계를 "참조만" 하는 명령어 (이동 X)

| 명령어 | 보는 곳 | 출력/효과 |
|---|---|---|
| `git status` | (0)↔(1), (1)↔(2), (2)↔(3) | 변경/스테이징/ahead·behind 표시 |
| `git diff` | (0) ↔ (1) | 워킹 변경 |
| `git diff --staged` | (1) ↔ (2) | 스테이징된 변경 |
| `git diff HEAD` | (0) ↔ (2) | 작업트리 vs 마지막 커밋 |
| `git log` | (2) 기준 커밋 그래프 | 로컬 히스토리 |
| `git log origin/main` | (3) 기준 커밋 그래프 | **fetch 시점의** 원격 히스토리 |

### git status가 비교하는 3쌍

`git status`는 정확히 다음 3쌍만 비교한다. **(4) 실제 서버는 절대 보지 않는다.**

```
작업트리 ── 인덱스 ── HEAD/refs/heads/main ── refs/remotes/origin/main ── 서버
   └──①──┘  └────②────┘                  └─────────③─────────┘            X
```

| # | 비교 | 출력 메시지 예시 |
|---|---|---|
| ① | (0) ↔ (1) | `Changes not staged for commit` |
| ② | (1) ↔ (2) | `Changes to be committed` |
| ③ | (2) ↔ (3) | `Your branch is ahead/behind by N commits` |

→ ③의 "behind"는 **마지막 fetch 시점 기준**이지 지금 이 순간의 서버 기준이 아니다.

## 실제 사례 — "어제 자동 수정 있었는데 왜 안 보이지?"

GitHub Actions가 야간에 콘텐츠를 자동 수정·커밋한 상황이었는데, 다음 날 아침 로컬에서 본 결과는 이랬다.

```bash
$ git status
On branch main
Your branch is up to date with 'origin/main'.
nothing to commit, working tree clean
```

겉보기엔 깨끗했지만 실제 서버에는 자동 커밋이 있었다. 원인은 `(3)`이 옛날 사진이었기 때문.

### fetch 전

```
(2) main                    = 4806c18  (내가 마지막 push한 커밋)
(3) origin/main (로컬 스냅샷) = 4806c18  ← status는 이 둘만 비교 → "up to date"
(4) 서버                    = b012ede  ← status가 절대 보지 않음
```

### fetch 후

```bash
$ git fetch origin main
   4806c18..b012ede  main       -> origin/main
```

```
(2) main                    = 4806c18
(3) origin/main (로컬 스냅샷) = b012ede  ← 이제 갱신됨
(4) 서버                    = b012ede

$ git status
Your branch is behind 'origin/main' by 1 commit, and can be fast-forwarded.
```

`(3)`이 최신화되자마자 비교 ③의 결과가 "behind 1"로 바뀌었다. status 자체는 똑같이 동작했고, **참조한 데이터의 신선도만 달라졌을 뿐**이다.

## 왜 Git은 자동 fetch를 안 하나

1. **오프라인 작업 보장** — `status`, `log`, `commit` 모두 네트워크 없이 동작해야 함
2. **속도** — 매번 네트워크 호출하면 IDE/CLI가 굼떠짐
3. **격리** — 원격 변경이 의도치 않게 로컬 상태 인식에 끼어드는 걸 막음

VS Code 상태표시줄의 `↓1` 같은 표시는 **VS Code가 백그라운드로 주기 fetch를 돌려서** 보여주는 것이지, Git 자체가 알려주는 게 아니다. CLI에서는 명시적으로 `git fetch`를 해야 한다.

## 핵심 정리

> - Git의 단계는 **(0) 작업트리 → (1) 인덱스 → (2) 로컬 브랜치 → (3) 원격 추적 → (4) 서버** 5단계
> - **`git fetch`만이 (4) → (3) 구간을 건드린다.** 나머지는 전부 로컬 ((0)~(3))만 본다
> - `git status`의 "up to date / behind"는 **(2) ↔ (3) 비교**이며, (3)은 마지막 fetch 시점의 스냅샷
> - 서버 상태를 신뢰하려면 `git fetch; git status` 순서로 확인해야 한다
> - `git pull` = `fetch` + `merge` 합본. (3)뿐 아니라 (2), (0)까지 자동으로 따라 움직인다는 점에 유의
